I want to build a small web app (and later mobile) for construction project milestones and risk impacts, to eventually integrate with Procore Scheduling.

Tech stack:

Frontend: React (single-page app is fine)

Backend: Node.js + Express (REST API)

Database: Postgres

The app has three main concepts:

Milestone WBS over 10 lifecycle stages

Change Events for milestone date changes

Company Impact Responses focused on main risks/issues

Business logic (summary)

There are 10 fixed project stages (WBS level 1):

Pre‑design and Concept

Design Development (Architecture, Structure, MEP)

Authority Approvals and NOCs

Detailed Design, Tender Documents and Contractor Award

Construction – Shell and Core

Construction – MEP Rough‑in, Blockwork and Exterior

Interior Fit‑Out and Finishes

External Works, Landscape and Final MEP

Completion Certificate, Snagging and Authority Handover

Client Handover and Defects Liability

Under these stages are Milestones (WBS level 2). Some are “stage gates” (e.g., ID concept/schematic/development approvals) and some are normal milestones.

Certain milestones are marked is_key_output = true (these correspond to typical milestone outputs like “Building Permit Issued”, “Practical Completion”, “Handover”).

If a milestone has is_key_output = true, any date change requires PM + Client sign-off.

If is_key_output = false, PM can approve the date change alone.

When an approved date change happens on a milestone, the system:

Updates that milestone’s current_date and previous_date

Creates impact records for all companies linked to that milestone

Notifies those companies via email + in-app to log main risks and issues

Companies should:

Only see detailed lists of milestones where they are explicitly linked.

But they should see a high-level stage timeline for context (showing the 10 stages and key output milestones with their own milestones highlighted).

For impact responses, I care mainly about main risks/issues, not detailed cost/time numbers. So each response should capture:

Risk level (None/Low/Medium/High)

Risk type (Time/Cost/Quality/Scope/Resources/Authority/Other)

Main risk/issue (short text)

Detailed comment (optional)
